## 1. 범위 및 원칙

### 포함
- 이메일 회원가입, 이메일 인증, 관리자 승인 및 접근 제어
- 필수 프로필 사진과 회원 프로필/필터 검색
- 관리자 공통 질문 관리, 회원 누적 답변(서술형·단일선택 객관식·밸런스게임)
- 벙 생성 신청/승인, 참석·취소 요청·대기열·수동 승격
- 예정/지난 벙, 참석자별·질문별 답변 탐색
- 복수 관리자 및 최고 관리자, 관리자 감사 기록

### 제외 (MVP)
- 실시간 채팅, 카카오톡 연동/대체, 결제, 공개 소모임 마켓플레이스, 복수 모임, 이벤트별 별도 질문, 팔로우/좋아요/댓글

## 3. 사용자 역할 및 접근 정책

- visitor: 로그인·회원가입·이메일 확인만 가능.
- pending/rejected/suspended: 본인 상태 및 허용된 계정 절차만 접근. 승인 회원 데이터 접근 금지.
- member(active): 본인 프로필/답변 관리, 승인 회원 프로필·답변 열람, 회원 검색, 벙 신청·참석·취소 요청, 참석자 답변 탐색.
- admin(active): member 권한 + 회원 가입 승인/반려/재신청 허용, 정지/복구, 질문 관리, 답변 숨김, 벙 승인/관리, 취소 요청 처리, 대기자 수동 승격, 개인별 참석 이력 조회.
- super_admin(active): admin 권한 + 관리자 임명/해제, 회원 탈퇴 처리, 감사 로그 조회, 서비스 설정.
- 최고 관리자 수는 여러 명 가능하나 최소 1명을 유지해야 함. 본인 권한을 변경해 마지막 최고 관리자가 사라지는 작업 금지.
- 인증·권한 검사는 UI뿐 아니라 서버와 Supabase RLS에서 수행. service role key는 클라이언트 노출 금지.

## 4. 화면 및 사용자 여정

### 라우트
- `/login`, `/signup`, `/pending`, `/account/rejected`, `/account/suspended`
- `/` 홈: FEVER 브랜딩, 회원 찾기/질문/벙 바로가기, 예정 벙 카드
- `/profile`, `/profile/edit`, `/profile/history` (본인)
- `/members`, `/members/[id]`
- `/questions`, `/questions/[id]`
- `/events`, `/events/new`, `/events/[id]`
- `/admin`, `/admin/members`, `/admin/requests`, `/admin/questions`, `/admin/events`, `/admin/roles`, `/admin/audit`, `/admin/settings`

### 회원가입
1. 이메일, 비밀번호, 닉네임, 출생연도, 거주지역, 프로필 사진 및 약관/개인정보 동의 입력.
2. 이메일 확인 후 관리자 승인 대기.
3. 관리자가 승인하면 보호된 서비스 이용 가능. 반려 시 재신청 허용 여부를 관리자만 변경.
4. 이메일 중복 및 닉네임 중복 차단. 사진은 회원가입 단계에서 필수.

### 프로필
- 사진(필수), 닉네임(필수), 출생연도, 거주지역, 성별/직업/MBTI/자기소개(선택), 사전 정의 관심사 태그.
- 상세 주소·전체 생년월일 수집하지 않음.
- 닉네임 변경 신청 후 기존 닉네임을 유지하며 관리자 승인 후 변경; 승인 시 고유성 재검증.
- 프로필의 누적 질문 답변은 카테고리별 조회 가능.
- 개인별 전체 벙 이력은 본인/관리자만; 단 개별 벙 상세의 참석자 명단은 모든 승인 회원에게 공개.
- 회원 목록 기본 정렬은 최근 가입순, 거주지역·나이대·직업·MBTI·관심사 필터 제공.

### 질문
- 질문 형식: text, single_choice, balance_game. 선택형은 단일 선택.
- 서술형 최대 300자, 회원당 질문별 답변 1개.
- 회원은 선택적으로 답변하고 수정/삭제 가능; 모든 승인 회원에게 공개.
- 이미 답변이 있는 질문은 의미/형식/선택지 변경 제한. 비활성화 후 새 질문 생성.
- 질문 비활성화 시 답변 보존하되 일반 조회에서는 숨김.

### 벙
- 생성 입력: 제목, 시작 일시, 장소, 설명, 정원(선택), 생성자.
- 생성 요청은 관리자 승인 전 비공개. 승인 시 생성자 자동 참석 등록.
- `capacity=null`은 무제한, 양수는 제한. 생성자 자동 참석을 고려해 정원은 최소 1.
- 대기자가 없고 여유가 있으면 신청 즉시 참석 확정. 정원 도달 또는 기존 대기자 존재 시 대기 등록.
- 참석 취소는 요청 상태로 보관, 승인 전까지 참석 확정 유지/정원 점유.
- 관리자가 취소 승인 시 자리 비움. 대기자 자동 승격 금지, 관리자가 수동 선택해 승격.
- 생성자 취소 승인 전 다른 승인 회원을 진행자로 지정해야 함.
- 종료된 벙의 참석자 명단은 운영상 수정 불가. 법적 개인정보 삭제는 비식별화 처리.
- 벙 상세는 모든 승인 회원이 볼 수 있으며 참석자 프로필과 답변을 사람별/질문별로 탐색.
- 지난 벙도 목록 및 상세 조회 가능. 답변은 회원의 최신 공개 답변 사용.

## 5. 권장 상태 모델 (구현 제안, 확정 정책과 구분)

### 회원
- `pending_email`, `pending_approval`, `active`, `rejected`, `suspended`, `withdrawal_requested`, `deleted`.
- 재신청 허용 플래그 또는 별도 요청 이력 테이블.

### 벙
- `pending`, `approved`, `rejected`, `cancelled`; 시작/종료 여부는 `starts_at`, 선택적 `ends_at` 기준 계산 권장.
- 종료된 벙 수정 금지 시점의 정의는 미확정 항목 참조.

### 참석
- `confirmed`, `waitlisted`, `cancelled`; 취소 요청은 별도 `participant_cancel_requests`에 `pending/approved/rejected`로 관리 권장.
- 대기 승격 및 정원 검사는 DB 트랜잭션/잠금 또는 동등한 원자적 서버 작업으로 처리.
- 관리자 직접 참석 등록도 중복·정원·대기열 우선 규칙을 일관되게 적용.

## 6. 데이터 모델 (논리 설계)

- `profiles`: auth user FK, nickname, nickname_normalized(unique), birth_year, region, gender, job, mbti, bio, avatar_path, membership_status, joined_at, created_at, updated_at.
- `user_roles`: user_id, role (`member`, `admin`, `super_admin`), assigned_by, assigned_at.
- `membership_requests`: user_id, status, reviewed_by, reviewed_at, rejection_reason, reapply_allowed.
- `nickname_change_requests`: user_id, proposed_nickname, status, reviewed_by, reviewed_at.
- `withdrawal_requests`: user_id, status, requested_at, processed_by, processed_at.
- `question_categories`: id, name, sort_order, is_active.
- `questions`: id, category_id, title, type, sort_order, is_active, created_at.
- `question_options`: id, question_id, label, sort_order.
- `answers`: id, user_id, question_id, text_value nullable, option_id nullable, updated_at, unique(user_id, question_id). DB constraint: 질문 유형에 맞는 답변 필드만 사용.
- `interests`: id, label, is_active, sort_order.
- `profile_interests`: user_id, interest_id, unique(user_id, interest_id).
- `events`: id, creator_id, host_user_id, title, description, location, starts_at, ends_at nullable, capacity nullable, approval_status, reviewed_by, reviewed_at, created_at.
- `event_participants`: id, event_id, user_id, status, joined_at, promoted_at nullable, unique(event_id, user_id).
- `participant_cancel_requests`: id, event_participant_id, status, requested_at, reviewed_by, reviewed_at, reason nullable.
- `admin_actions`: id, actor_id, action, target_type, target_id, metadata, created_at.
- `service_settings`: singleton, service_name, logo_path, description.

모든 타임스탬프는 UTC 저장, 한국 시간으로 표시. 정원·대기열 처리 시 DB 수준 무결성 보장. 사진은 private bucket 및 접근 권한 검사. 승인 회원 전용 데이터 조회는 RLS로 강제.

## 7. 관리자 화면

- 대시보드: 승인 대기 가입, 닉네임 변경 요청, 탈퇴 요청, 벙 승인 대기, 참석 취소 요청, 대기자 현황.
- 회원: 승인/반려, 재신청 허용, 정지/복구, 닉네임 변경 승인/반려, 탈퇴 요청 처리(최고 관리자).
- 질문: 카테고리/질문/선택지 관리, 비활성화, 답변 숨김.
- 벙: 승인/반려, 수정/취소, 참석자 등록, 참석 취소 요청 처리, 대기자 수동 승격, 진행자 변경.
- 역할: 최고 관리자만 관리자 임명/해제, 최소 1명 최고 관리자 유지.
- 감사 로그: 최고 관리자만 열람; 승인/정지/탈퇴/닉네임 변경/벙 처리/역할 변경 기록.

## 8. 디자인 가이드

- 이전 FEVER 시안 기반: 딥그린, 세이지그린, 크림화이트, 둥근 카드, 모바일 우선.
- 하단 내비게이션: 홈 / 모임 / 벙 / MY.
- 회원 모바일 UI 우선, 관리자 화면 PC 친화적 반응형.
- 접근성: 충분한 터치 크기, 폼 라벨, 로딩/빈 상태/오류 상태, 대비와 키보드 접근성.

## 9. 필수 예외 및 수용 테스트

1. 미승인/정지/반려 회원이 직접 URL/API/Storage URL로 다른 회원 데이터를 조회할 수 없어야 한다.
2. 회원 A는 회원 B의 프로필·답변을 수정할 수 없어야 한다.
3. 닉네임 변경 대기 중에는 기존 닉네임 유지; 동시 승인 중복 차단.
4. 선택형 답변은 유효한 선택지 하나만 허용, 서술형은 300자 초과 저장 차단.
5. 이미 답변된 질문의 내용/형식/선택지 의미 변경 차단.
6. 같은 벙 중복 참석/중복 대기 차단.
7. 마지막 한 자리 동시 신청 시 한 명만 확정; 나머지는 대기.
8. 대기자가 있는 동안 빈자리가 생겨도 신규 신청은 대기열에 추가.
9. 취소 요청 중인 참석자는 계속 정원 점유; 관리자 승인 시에만 제외.
10. 취소 승인으로 빈자리가 생겨도 자동 승격되지 않음.
11. 관리자가 대기자를 수동 승격할 때 정원 초과 및 중복을 차단.
12. 진행자 본인의 취소 요청은 새 진행자 지정 전 승인 불가.
13. 지난 벙 참석자 명단 운영상 변경 불가; 탈퇴 회원 개인정보는 별도 비식별 처리.
14. 개별 벙 참석자 목록은 모든 승인 회원이 열람 가능하지만 개인별 전체 벙 이력은 본인/관리자만 조회.
15. 마지막 최고 관리자 제거/탈퇴 처리 불가.
16. 일반 관리자는 최고 관리자 전용 기능과 감사 로그에 접근 불가.
17. 프로필 사진 업로드 실패 시 기존 사진 보존, 가입 시 사진 없으면 완료 불가.
18. 모든 핵심 관리자 조작에 감사 로그 기록.

## 10. 남은 미확정 사항 (Codex가 임의 결정하지 말 것)

- **벙 종료 기준**: 시작 시각 이후 자동 종료인지, 종료 시각 필수인지, 관리자가 종료하는지. 지난 벙 명단 잠금 시점과 직접 연결됨.
- **정원 미설정 벙의 대기열 처리**: 무제한 벙에는 대기열을 사용하지 않는 것으로 권장하나 명시 확인 필요.
- **대기자 수동 승격 순서**: 관리자 임의 선택 허용인지, 대기순서 준수인지. 현재 '수동 승격'만 확정.
- **벙 생성자 외 진행자 변경 가능 시점 및 권한**: 생성자 취소 시 새 진행자 지정은 확정; 그 외 변경은 미확정.
- **벙 취소 요청의 거절/철회 및 대기자의 대기 취소 방식**: 운영 규칙 미확정.
- **닉네임 정규화 세부 규칙**: 공백/대소문자/특수문자 허용 범위, 변경 요청 빈도.
- **필수 프로필 사진 규격**: 최대 파일 크기, 허용 형식, 이미지 리사이즈.
- **선택형 질문의 선택지 개수 제한**, 객관식과 밸런스게임의 세부 UI.
- **회원 탈퇴 시 처리 기한·보존 항목**: 법적 의무에 맞게 확정 필요. 관리자 처리 정책이 개인정보 삭제권을 제한해서는 안 됨.
- **알림 채널**: 이메일 알림을 보낼지, 웹 내 알림만 제공할지. MVP 기본은 상태 화면/관리자 대시보드로 제안.
- **기존 카카오톡 회원 검증 방법**: 승인 기준은 운영자 수동 판단, 별도 카카오 연동은 범위 밖으로 제안.
- **회원 가입 후 기본 필수 정보 범위**: 출생연도·지역·사진·닉네임은 가입 입력으로 제안되었으나 사진 외 필수 여부를 재확인할 수 있음.

위 항목은 서비스 출시 전 결정해야 하며, Codex는 확정 정책과 제안 정책을 혼동해서는 안 된다. 개발에 영향이 없는 세부사항은 기본값을 문서화해 제안하고, 비즈니스 규칙을 변경하는 사항은 반드시 사용자에게 확인한다.

## 11. 단계별 구현 계획

1. **Phase 1 — 기반**: Next.js/TS/Tailwind, Supabase 연동, 환경변수, 레이아웃, 라우트, 초기 마이그레이션.
2. **Phase 2 — 인증/승인**: 가입, 이메일 인증, 사진, 승인 대기, 관리자 승인, RLS, 역할.
3. **Phase 3 — 프로필/회원 탐색**: 프로필 편집, 닉네임 변경 요청, 필터, 회원 상세, 개인 이력 접근 제어.
4. **Phase 4 — 질문**: 카테고리, 서술형/선택형, 누적 답변, 비활성화, 관리자 화면.
5. **Phase 5 — 벙**: 생성/승인, 참석/취소 요청, 정원/대기열, 수동 승격, 종료 잠금, 참석자 답변 탐색.
6. **Phase 6 — 운영/배포**: 탈퇴/정지, 감사 로그, 테스트, 보안 검토, 모바일 QA, Vercel 배포.

각 Phase 종료 시: 변경 파일, 마이그레이션, 테스트 결과, 남은 이슈를 보고하고 다음 단계로 넘어가기 전에 승인받는다.

## 12. Codex 공통 지시

- 이 PRD의 '확정 정책'을 우선하며 기능을 임의로 삭제·추가·변경하지 않는다.
- '남은 미확정 사항' 중 구현에 영향을 주는 결정은 코드 작성 전에 질문한다.
- 서버·DB 권한 검증 및 원자적 참석 처리에 우선순위를 둔다.
- 처음에는 Phase 1만 구현하고, 완료 후 작업 내용을 보고한다.
- 비밀 키, 인증 토큰, 개인정보를 코드나 로그에 남기지 않는다.
- SQL 마이그레이션, RLS 정책, 주요 상태 전이 및 회귀 테스트를 포함한다.
